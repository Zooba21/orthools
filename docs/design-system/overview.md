# Design System — Orthools

## Philosophy

Three constraints shape every decision here:

1. **WCAG 2.1 AA is non-negotiable.** This tool may be used in clinical and healthcare institutions. Accessibility is a compliance requirement, not a nice-to-have.
2. **Clean, professional aesthetic.** The platform targets medical professionals. It should feel clinical and precise — not generic SaaS. The target look is shadcn/ui: neutral palette, minimal decoration, good typography, generous whitespace.
3. **No styling framework sprawl in feature code.** The component and page code that developers read day-to-day should reference semantic names (`<Button>`, `<Card>`), not utility class chains. Tailwind classes live inside `ui/` component implementations and layout scaffolding — not in domain feature templates.

---

## Stack decision

| Layer | Choice | Reason |
|-------|--------|--------|
| Component library | **shadcn/ui** | Copy-own Radix primitives with Tailwind styling; full control over source; accessible by default via Radix. |
| Headless primitives | **Radix UI** (ships inside shadcn) | Focus management, live announcements, overlays, accessible comboboxes — all built in. |
| Theming | **CSS custom properties** (`globals.css`) | Single source of truth for all design tokens. Uses the shadcn naming convention (`--background`, `--primary`, etc.) in oklch. |
| Custom component styles | **CSS Modules** (`.module.css` co-located) | Scoped styles for custom components that go beyond shadcn primitives. No class sprawl in JSX templates. |
| Tailwind | **Used as shadcn's styling engine** | Utility classes are encapsulated inside shadcn component source. Feature templates call `<Button variant="outline">` — no visible class chains. |
| Visual development & WCAG verification | **Storybook** with `@storybook/addon-a11y` — runs axe-core per story |

## Token system

`src/styles/globals.css` is the single source of truth for all design tokens. It uses the **shadcn naming convention** (bare names, no prefix: `--background`, `--primary`, `--border`…) and the **oklch color space** throughout. The tokens were generated by the shadcn/ui theme generator and hand-tuned for the Orthools branding.

The file defines the vocabulary used everywhere:
- Custom component CSS Modules: `color: var(--foreground)`
- shadcn component config in `tailwind.config.ts`: maps `--primary` → `primary` Tailwind colour
- Dark theme override: `.dark { ... }` block on the `html` element

> The `@theme inline { }` block from the shadcn generator output is only included when using Tailwind v4's CSS-first config. For Tailwind v3, token integration is done via `tailwind.config.ts` `extend.colors`.

### The cascade trick — write once, works in both themes

```css
/* globals.css */
:root {
  --primary: oklch(0.3118 0.0622 230.0593);
}

.dark {
  --primary: oklch(0.5198 0.0936 223.1280);
}
```

Tailwind's `bg-primary` and `text-primary` resolve to the active `--primary` value automatically. **No per-component dark-mode variants needed for brand colours.** Override the token; all consumers follow.

| Token | Role |
|-------|------|
| `--background` | Page background |
| `--foreground` | Primary text |
| `--card` | Card / panel surface |
| `--card-foreground` | Text on cards |
| `--popover` | Overlay / dropdown surface |
| `--primary` | Primary action |
| `--primary-foreground` | Text on primary |

| `--muted-foreground` | Secondary text, placeholders |
| `--accent` | Tertiary accent |
| `--destructive` | Error / danger |

| `--input` | Input field border |
| `--ring` | Focus ring |
| `--radius` | Base border radius |

`globals.css` is the only place where visual tokens are defined. No scattered overrides in feature CSS files.

## Component layers

### `ui/` — design system components

Components in `ui/` have no domain knowledge. They fall into two groups:

**shadcn/ui extensions with configuration:** When a shadcn component needs a consistent pre-configuration across the app (a specific variant, icon slot, fixed size), a thin wrapper codifies that convention. For example, `AppButton` always renders `<Button variant="outline">` with correct sizing — callers don't set variants. Only created when a convention needs enforcing; raw shadcn components are used directly otherwise.

**Genuinely custom components:** Components where shadcn/Radix has no equivalent (`ColorDot`) or where clinical/domain-specific visual requirements make a custom implementation necessary. `ColorDot` renders a runtime hex color on a circle, checks WCAG contrast against the clinical background, and exposes size variants for the execution view.

```
presentation/ui/
├── button/
│   └── button.tsx             # Extension: shadcn Button + variant convention
├── card/
│   └── card.tsx               # Extension: shadcn Card + token-aware surface
├── form-field/
│   └── form-field.tsx         # Extension: shadcn FormField + 'outline' appearance
├── data-table/
│   └── data-table.tsx         # Extension: shadcn Table + pagination + sort
├── color-dot/
│   ├── color-dot.tsx          # Custom: hex color circle, size variants
│   └── color-dot.module.css
└── badge/
    └── badge.tsx              # Custom: status indicator
```

For everything else (form validation messages, icons, progress indicators, dialogs) shadcn/ui is used directly — no wrapper needed. A wrapper is only justified when it encodes a convention the whole codebase must respect.

### Domain components

Domain components live inside the module's `components/` folder. They know the domain vocabulary (`Instruction`, `Category`, `Slide`) and compose `ui/` components with domain data. They never appear in `ui/`.

```
presentation/lexical-evocation/components/
├── instruction-row/         # Knows what an Instruction is
├── slide-card/              # Uses ui/color-dot + ui/card
└── category-selector/       # Uses shadcn Select + domain Category tree
```

## Storybook

### Why it is justified for this project specifically

Storybook is not always worth its setup cost. For this project, three concrete reasons tip the balance:

**1. The a11y addon is the WCAG verification workflow.**
`@storybook/addon-a11y` runs axe-core automatically on every story render. Each `ui/` component story becomes a live WCAG AA check — colour contrast, ARIA roles, keyboard focus, label associations. This is the fastest feedback loop available short of a full accessibility audit. For a clinical tool, this is not optional.

**2. `ColorDot` requires visual regression testing across colour space.**
The component renders a runtime hex color. It has three size variants (normal, large for execution, small for preview thumbnails) and must always meet WCAG 4.5:1 contrast against its background. Verifying this manually is infeasible. A story with a colour picker control and an overlaid contrast ratio display makes it testable in seconds.

**3. Storybook stories compile to Vitest tests.**
`@storybook/experimental-addon-test` maps stories to Vitest test cases without any duplication. A story written for visual development becomes a component interaction test. One file, two purposes.

### What to story

Write stories for:
- Every component in `ui/` — all variants, all sizes, all states (default, hover, focus, disabled, error, loading)
- `ColorDot` — a story with a hex colour control and contrast ratio indicator
- `SlideCard` — colour-only slide, colour + audio slide, non-action slide
- shadcn theme alignment — a story page showing all used shadcn components side-by-side to visually verify the custom aesthetic

Do not story:
- Pages (tested via render() integration tests + Playwright)
- Hooks (tested via renderHook())
- Domain entities and use cases (pure unit tests)

### File placement

Stories are co-located with the component, not in a separate `stories/` folder.

```
presentation/ui/color-dot/
├── color-dot.tsx
├── color-dot.module.css
├── color-dot.spec.tsx            # React Testing Library unit test
└── color-dot.stories.tsx         # Storybook story (also compiles to Vitest)
```

### Accessibility workflow

For every `ui/` component, the definition of done includes:

1. Story renders without axe errors in the a11y addon panel.
2. Keyboard navigation works as expected (Tab, Enter, Escape where applicable).
3. Color contrast check passes at WCAG AA level (4.5:1 for text, 3:1 for UI components).
4. Story covers the focus-visible state explicitly.

The a11y panel in Storybook shows violations inline, with the specific WCAG rule and the failing element highlighted. This is the fastest path to catching regressions before they reach a PR.

## The execution view — special case

The execution screen is full-screen, patient-facing, and visually distinct from the rest of the app. It uses `--clinical-bg` as the background and a large `ColorDot` variant. During execution:

- No nav shell or app chrome — route rendered outside the shell layout.
- The colour dot is the only visual element (optionally an audio indicator).
- `focus-trap-react` locks keyboard focus within the execution area.
- An `aria-live="assertive"` region announces slide transitions for screen readers.
- A Storybook story for the execution view renders the full-screen layout in an iframe to verify contrast and visual hierarchy in isolation.

## Future: dark mode and high-contrast patient theme

The token system is structured to support multiple themes. A `[data-theme="clinical-high-contrast"]` attribute on the root element can override tokens for a patient-accessible variant with stronger contrast and larger touch targets. This does not require changing any component — only the token values change.

Dark mode is already wired: `.dark { ... }` overrides are in `globals.css`. A `useTheme` hook (from shadcn's theme provider pattern) toggles the class on `<html>`.
